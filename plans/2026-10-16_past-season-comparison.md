## 1. やりたいこと

雪のシーズンが始まって今シーズンのデータが表示されるようになったら、
**今年と去年を見比べられるようにしたい。**

切り口は3つある。**どれをやるかで難易度が変わる。**

| | 内容 | 難易度 | 目安 |
|---|---|---|---|
| **A** | **年を切り替えて表示**（今年 ⇄ 去年） | 易 | 半日 |
| **B** | **数値パネルに「去年の同日」を添える** | 易〜中 | 半日 |
| **C** | **グラフに去年を重ねて描く** | 中 | 1日 |

当初の相談はAだったが、**毎朝の道具としてはBのほうが効く可能性がある**（「4. Bを推す理由」参照）。

---

## 2. なぜ易しいのか：データはもう全部ある

`snow_data_history.csv` に **17シーズン分・8,796行**が入っている。**新しく集める必要はない。**

```
2022年度  151日
2023年度  182日
2024年度  181日
2025年度  151日   ← 去年
```

`collect.py` は毎回CSV全体からJSONを作り直しているので、**いつ着手しても過去分は失われない。**
「今シーズンが始まると去年のデータが消えてしまうのでは」という心配は不要。

---

## 3. 必要な変更

### 3-1. `collect.py` — 去年の分をJSONに足す（約30行）

**既存のキーを一切壊さず、追加だけにするのが肝。**

```json
{
  "generated_at": "...",
  "season": "2026-27",
  "latest": { ... },          ← そのまま
  "series": { ... },          ← そのまま（今シーズン）

  "previous": {               ← ここだけ追加
    "season": "2025-26",
    "series": { "dates": ["2025-11-01", ...], "新井消防署": { "snowfall_cm": [...], "snowdepth_cm": [...] } },
    "by_date": { "12-15": { "新井消防署": { "snowdepth_cm": 38, "snowfall_cm": 5 } } }
  }
}
```

`by_date` を「月-日」をキーにした索引にしておくと、**画面側が「去年の同じ日」を一発で引ける。**

サイズの増分は **gzip後で約1.7KB**（いまの初回通信78KBに対して誤差）。

### 3-2. `docs/index.html` — 切り替えUI（約50行）

地点タブの上に、年度のタブをもう1列足す。

```
[2026-27]  [2025-26]        ← 追加
[新井] [頸南] [妙高支所]      ← 既存
```

### 3-3. `docs/service-worker.js` — バージョンを上げる（数行）

`VERSION` を `v3` に。古いキャッシュが `activate` で消える。

## 4. Bを推す理由

毎朝3秒で見る画面で、**グラフを切り替えて見比べる人がどれだけいるか**は疑問。

それより、数値パネルにこう出ているほうが、朝の会話に近い。

```
新井消防署        42 cm
前日比 +15  降雪 18cm
去年の同日 38cm（+4）      ← これ
```

**「去年より多いのか少ないのか」は、雪国の人がいちばん話題にすること**ではないか。
実装も軽く、画面も混まない。`by_date` の索引さえ作れば、**引いて引き算するだけ。**

---

## 5. つまずきそうな点（5つ）

### 5-1. キャッシュの食い違い【最大の落とし穴】

Service Worker は**HTMLとJSONを別々にキャッシュしている。**
更新後、**新しいHTMLと古いJSONの組み合わせ**が一瞬できうる（特にオフライン時）。

対策は2つ。

- **追加だけの変更にする**（3-1）。古いHTMLは `previous` を無視するだけなので壊れない
- 新しいHTML側に `if (data.previous)` の防御を入れる

**これはPWA特有の問題**で、普通のサイトなら起きない。

### 5-2. シーズンごとに期間が違う

2025-26は11/1〜3/23だが、**2022-23には11月のページが存在しない。**
重ねるときに配列の長さが揃わないので、**「月-日」で突き合わせる**必要がある。

### 5-3. 欠測が多い

去年の線は**あちこち途切れる**（全日欠測の組み合わせが42件あることは調査済み）。
「線をつなぐか、切るか」を決める必要がある。**切るほうが正直。**

### 5-4. スマホの画面が混む

375pxに**線2本＋棒2種**は読めない。現実的な落としどころは、

- **去年は積雪の線だけ**を点線・薄い色で重ねる
- 降雪の棒は今年だけ

### 5-5. うるう年

2/29は4年に1度しかない。「去年の同日」が存在しない日が出る。
ごく稀だが `null` の処理が要る。

## 7. 進め方（着手するとき）

段階を分けると、**途中で止めても価値が残る。**

1. `collect.py` に `previous` を足す（画面は変えない）
2. 数値パネルに「去年の同日」を出す ← **ここだけで価値が出る**
3. グラフの切り替え／重ね表示（余力があれば）

1と2だけなら半日かからない見込み。

### 雪を待つ必要はない

**2025-26 と 2024-25 を使えば、本番とまったく同じ条件のリハーサルになる。**
両方とも実データが揃っているので、**11月を待つより、いま作ったほうが検証しやすいくらい。**

---

## 8. この冬に見ること（判断材料）

**作るかどうかより先に、「使われているか」を見る。**

| 観察すること | 判断への効き方 |
|---|---|
| そもそも毎朝開いているか | 開いていないなら、機能を足しても意味がない |
| **グラフまでスクロールしているか／数値だけ見て閉じるか** | 数値だけなら **B**、グラフも見るなら **A・C** |
| 「去年はどうだったか」と思う場面が実際にあるか | 無ければ作らない |
| 知人（1〜2名）の反応 | 「毎朝見たくなるか」だけを聞く |
| `status.json` の `latest_observed_date` | cronの実行時刻の判断材料（別件） |

**何も思わなければ作らない**のが正しい。Phase 3は「冬の楽しみ」として置いてあるもので、
機能を増やすこと自体が目的ではない。

## 9. もうひとつ先の話

同じ仕組みで**全18シーズンをJSONに入れることもできる**（gzip後38KB）。

そうすると、**Streamlit版の「年月を選んで見る」機能をスマホに持ってくる道**が開ける。
[構成と将来の検討メモ](../Documents/de-streamlit_notes.md) の3章で「技術的な制約はない」と書いたのは、この話。

ただし**画面設計が別物になる**（3つの条件を選んで並べるUIは375pxに載らない）ので、
**別の企画として考えるべき。**この検討メモの範囲外とする。
