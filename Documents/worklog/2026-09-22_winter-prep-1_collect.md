## なぜ作り替えるのか（記事の導入に使える部分）

このアプリは、妙高市が公開している雪の観測データをグラフにするだけの、実質1画面のStreamlitアプリだった。
動いてはいる。ただ、**この冬から毎朝スマホで使う道具にする**と決めた瞬間に、3つの問題が表に出てきた。

### ① 保存したはずのデータが消えている

過去のデータをCSVに書き足す処理（`save_history_data()`）は書いてあった。ローカルでは動く。
けれど Streamlit Community Cloud のファイルシステムは一時的なもので、**アプリが再起動するたびに書いたものが消える**。
つまりクラウド上では、過去データの蓄積は最初から機能していなかった。

> 入門者向けの学びとしてはここが一番大きい。「書き込むコードがある」ことと「データが残る」ことは別物で、
> **どこで動いているかによって、同じコードの結果が変わる**。

### ② アプリが寝てしまう

Community Cloud は、しばらく誰も見ないとスリープする。復帰に数十秒かかる。
「少人数が毎朝1回だけ見る」という使い方と、これ以上ないほど相性が悪い。

### ③ そもそも構造が合っていない

観測は**1日1回、朝9時**。データはそれ以外の時間には変わらない。
なのに旧版は、**画面を開くたびに**市のサイトへ取りに行っていた。

- 遅い（毎回ネットワーク待ち）
- 市のサーバーに無駄な負担をかける
- 取得が失敗しても、画面を開いた人が「なんか出ないな」と思うだけで終わる

**更新の頻度と取得の頻度が合っていない**のが根っこだった。

### 作り替えたあとの形

```
GitHub Actions（毎朝1回）
  └ collect.py … 市のサイトから取得
       ├ snow_data_history.csv  全シーズンの正
       ├ data/snow_data.json    最新シーズン（表示用）
       └ data/status.json       実行記録
                  ↓ 自動でコミット
Streamlit版 … 保存されたCSVを読むだけ。取りに行かない
静的サイト（次回）… JSONを読んで描く
```

サーバーなし。費用ゼロ。**GitHubのリポジトリがそのままデータベースになる。**

## この日いちばん頭を使ったところ：「まだ無い」を失敗にしない

作業した2026年9月は**オフシーズン**。市のサイトの最新は2026年3月で、次のシーズンのページは11月に出る。

つまり9月〜10月は、**新しい数字が1つも出ない状態で毎朝の自動実行を回す期間**になる。
ここで「データが取れなかった＝失敗」と作ってしまうと、**6週間、毎朝失敗メールが届く**。
そして人は、毎日届く警告を必ず無視するようになる。

> **これは「直そうとしている問題より悪い状態」。**
> もともとの問題は「壊れても気づかない」こと。毎朝オオカミ少年のメールを送る仕組みは、
> **気づける仕組みを自分の手で殺してしまう。**

そこで、失敗の定義を先に決めてから実装した。

| 状況 | 扱い |
|---|---|
| インデックスページが取れない（HTTPエラー等） | **失敗**（市のURL変更かもしれない。人が見るべき） |
| 月別リンクが1件も見つからない | **失敗**（ページ構造が変わった） |
| ページはあるのに、テーブルや日付行が取れない | **失敗**（HTML構造の変更。冬なら即知りたい） |
| 既存データと矛盾する（日数が大幅に減る等） | **失敗**（静かなデータ破壊を防ぐ） |
| **当シーズンのページがまだ無い** | **成功**（オフシーズンの正常な状態） |
| 今日の行がまだ「-」（欠測） | **成功**（更新前に取りに行っただけ） |
| 変化がなくコミットするものが無い | **成功** |

### 「11月だからページがあるはず」と書いてはいけない

例年、新シーズンのページは11月に出る。だから「11月になったのにページが無ければ失敗」としたくなる。
けれど実際に市のサイトを調べると、**17シーズンのうち11月のページがあるのは12シーズンだけ**だった。
暖冬などで11月に雪が降らなければ、市は11月分を出さない年がある。

**もし暦の月で判定していたら、5シーズン分、1か月まるごと失敗メールが届いていた。**

判定基準は「**新しいページが出たかどうか**」の一点だけにした。
裏を返すと、シーズンの切り替わりは完全に自動発見まかせになる。
11月のある朝、市がページを公開した瞬間に、仕組みが勝手に拾いはじめる――これが今回のねらい。

## 作ったもの

### `collect.py`（696行）

旧 `main.py` の中にあったスクレイピング処理3つ（`_pick_data_table()` / `_to_float_or_none()` / `fetch_snow_data()`）を、
**Streamlitに一切依存しない形**で独立させた。`@st.cache_data`（キャッシュ）と `st.error()`（画面へのエラー表示）を外し、
ログと戻り値だけで完結させている。

```bash
python collect.py            # 当シーズンの最新月ページ1枚だけ取得（毎朝これが走る）
python collect.py --all      # 全期間バックフィル（初回に1回だけ）
python collect.py --dry-run  # 取得して表示するが、ファイルは書かない
```

> **`--dry-run` は入門者にこそ勧めたい。**「本番と同じ処理を走らせるが、何も壊さない」モードがあると、
> 怖がらずに何度でも試せる。今回も、実際に動かして確かめる作業のほとんどがこれで済んだ。

**市のサーバーへの礼儀**として、毎朝の実行で取りに行くのはインデックス1枚＋当シーズンの該当月1枚の**計2回だけ**。
全月を毎日取り直すようなことはしない。`--all` は初回専用で、1.5秒間隔を空けて回す。

### 月別URLの自動発見（手作業の廃止）

旧版は、新しい月が公開されるたびに `data_urls.csv` へ**手で1行足す**運用だった。
**冬の最中に手作業が挟まると、忘れた日にアプリが止まる。** ここを自動化した。

市のインデックスページのリンクは、こういう文字列になっている。

```
令和7年度 降積雪観測(R8.3)      → /docs/78543.html
令和7年度 降積雪観測(R7.11)     → /docs/75618.html
平成30年度 降積雪観測（H31.4）  → /docs/392.html
```

ここには**実際に踏んだ落とし穴**がいくつもある。記事にするならこの部分が具体的で面白いはず。

- **先頭の「令和7年度」は信用できない。** 市のサイト側で不整合があり、R8.3もR7.4も同じ「令和7年度」と書かれている。
  なので **`(R8.3)` の括弧の中だけを信じて、年度は自分で計算する**
- **括弧が半角 `()` と全角 `（）` で混在**している。`H26.04` のようなゼロ埋めもある
- 和暦の変換：**令和n年 = 2018 + n**、**平成n年 = 1988 + n**
- **月を11〜4月に決め打ちしてはいけない。** `平成23年度 降積雪観測(H24.05)` という**5月のページが実在する**

`data_urls.csv` は消さずに残したが、**役割が変わった**。
手で追記する台帳ではなく、**毎朝インデックスから作り直される派生ファイル**になった。

## 直したバグ：正規表現がマイナスを見ていなかった

旧版のこのコードには、静かなバグがあった。

```python
# 旧（バグあり）
match = re.search(r'\d+(?:\.\d+)?', x)   # "-5" から "5" だけを拾ってしまう
```

`\d` は数字だけを表す。マイナス記号は含まれない。
つまり `"-5"` を渡すと **`5.0` が返る**。符号が消える。

そしてこの結果、main.py にあった「負の値なら `None` にする」というガードは、
**一度も発火しない死んだコード**になっていた。負の値がそこへ到達できないのだから当然だ。

> **バグが2つ重なって、見た目には何も起きていなかった。**
> 「異常値を弾く処理を書いた」つもりが、弾く対象が手前で消されていたので、永遠に動かない。
> テストがないコードで起きがちな、いちばん気づきにくい壊れ方。

直し方は2段階。

```python
# 新
match = re.search(r'-?\d+(?:\.\d+)?', x)  # 符号を拾う
```

そのうえで、**負の値を `None` に潰すのをやめた**。そのまま保存して、**警告ログを出す**。
理由は、潰してしまうと「市のデータがおかしいのか、自分のパースが間違っているのか」を後から切り分けられなくなるから。

### そして初回の実行で、いきなり2件釣れた

```
[WARNING] 積雪量が負値です（そのまま保存します）: 2024年2月3日 新井消防署 raw='-18' -> -18.0
[WARNING] 積雪量が負値です（そのまま保存します）: 2024年3月3日 新井消防署 raw='-10' -> -10.0
```

市のページのHTMLを直接見に行って確認したところ、セルの中身が本当に `-18` だった。前後の日は 21cm と 15cm。
**市の入力ミスと見てまず間違いない。** パースの副産物ではない。

積雪がマイナスになることは物理的にありえない。でも**データにはありうる**。
「ありえない値を見なかったことにする」のではなく、**残して警告する**ほうが、後で真相にたどり着ける。

## もうひとつの発見：存在しない「4月31日」

全期間バックフィルの結果を点検していて、4月のデータが 90行（30日×3地点）のはずなのに、
**2015年4月と2025年4月だけ93行**になっていることに気づいた。

市のページを見に行くと、4月の表の最後に**空っぽの「31日」の行**があった。テンプレートの消し忘れだろう。

```
['31日', '', '', '', '', '', '']
['降雪量月計', '-', '2', '0']
```

値は全部空なので害はない。ただ、存在しない日付がデータに混ざっているのは気持ちが悪いし、
日付として扱う処理（グラフの横軸など）で事故のもとになる。

対処は2か所に入れた。

1. **取り込むとき**に、その月に実在しない日は弾く（`calendar.monthrange()` で月の日数を見る）
2. **CSVを読むとき**にも同じ判定をして落とす

なぜ2か所か。今回のデータ更新は **upsert**（同じ日のデータがあれば置き換える）方式なので、
**すでに入ってしまった行を消す経路がない**。読み込み側にも判定を置くことで、次に走ったときに自然と消える
（実際、次の実行で「実在しない日付の行を履歴から除きます: 6行」と出て消えた）。

> **自分で自分を直す仕組み**を1つ足しておくと、手作業で直しに行かなくてよくなる。

## 追記ではなく upsert にした話

旧版は、取得したデータを履歴CSVに**追記**していた。
これは過去の月なら問題ないが、**当月のデータは日々増えるし、訂正も入る**。
追記のままだと、同じ日の行がどんどん増えていく。

そこで **`(年, 月, 日, 観測地点)` をキーにした upsert**（あれば置き換え、なければ追加）にした。
何度実行しても結果が同じになる。これを「**冪等（べきとう）**」という。

自動で毎日走る仕組みを作るとき、**冪等かどうかは死活問題**になる。
「途中で失敗したからもう一度流す」が安全にできるかどうかが、ここで決まる。

## 次にやること

- **タスク4**：GitHub Actions のワークフローを作る。毎朝10:30 JST（cron `30 1 * * *`）。
  手動実行で緑になることと、**わざと失敗させてメールが届くこと**を確認する
- **タスク5**：Streamlit版からスクレイピングを外し、保存されたCSVを読むだけにする
- **次回（冬支度②）**：JSONを読んで描く静的サイト＋PWA

### 実行時刻を10:30にした理由

計画では9:30と書いていた。観測は9時だから、という理由で。
けれど**そのデータが市のサイトに載る時刻は確認していない**。
早すぎると「取得は成功したが、今日の行はまだ空」という状態が毎朝続く。
これは**記録上は成功なのに中身が古い**という、いちばん気づきにくい壊れ方になる。

まず10:30で始めて、10月の無人稼働を観察してから前倒しする。
そのために `status.json` に「取得できた最新の観測日」を記録するようにした。
11月に入れば、毎朝それが当日になっているか前日のままかが、Gitの履歴から読める。

（GitHub Actionsのcronは混雑で数分〜数十分遅れる。特に毎時0分が混むので `:30` にしてある。）

## 記事にするときの切り口メモ

書き手向けのメモ。どれも今回実際に起きたこと。

1. **「まだ無い」を失敗と呼ばない設計**
   通知が毎日届く仕組みは、それ自体が通知を殺す。何を失敗と呼ぶかを先に決める話
2. **暦で判定してはいけなかった話**
   「11月＝雪のシーズン」は人間の常識。データは5シーズンでその常識を裏切っていた
3. **重なって見えなくなっていたバグ**
   `\d+` が符号を落とす → 異常値チェックが永遠に発火しない。バグが2つあると症状が消える
4. **異常値は潰さず、残して警告する**
   潰すと「市が間違えたのか、自分が間違えたのか」が二度と分からなくなる。実際に2件釣れた
5. **手で書いた台帳は必ず間違える**
   誤ったラベルが1件混ざっていて、自動生成に切り替えたら勝手に直った
6. **冪等であること**
   追記から upsert へ。「もう一度流す」が怖くない状態を作る
7. **コードがあることと、データが残ることは別**
   Streamlit Cloud の一時ファイルシステム。入門者がいちばん引っかかる場所かもしれない
