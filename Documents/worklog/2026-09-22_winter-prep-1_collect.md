## ■ なぜ作り替えるのか（記事の導入に使える部分）

第9回まででアプリは完成し、Streamlit Cloud で公開もした。動いている。
けれど、**この冬から毎朝スマホで使う道具にする**と決めた瞬間に、3つの問題が表に出てきました。

### ① 保存したはずのデータが、消えている

過去のデータをCSVに書き足す処理（`save_history_data()`）は、ちゃんと書いてありました。
手元のパソコンでは、たしかに保存されます。

ところが Streamlit Cloud のファイル置き場は一時的なもので、
**アプリが再起動するたびに、書いたものが消えてしまいます。**

つまりクラウド上では、過去データの蓄積は最初から機能していませんでした。

> 入門者向けの学びとしては、ここがいちばん大きいかもしれません。
> **「保存するコードがある」ことと「データが残る」ことは、別の話**なんですね。
> 同じコードでも、**どこで動かしているかによって結果が変わる**。

### ② アプリが寝てしまう

Streamlit Community Cloud は、しばらく誰も見ないとスリープします。起こすのに数十秒かかります。
これは第9回の記事でも「アプリがスリープしている時は青いボタンを押してください」と書いた、あの挙動です。

「少人数が毎朝1回だけ見る」という使い方とは、これ以上ないほど相性が悪いのです。

### ③ そもそも、構造が合っていなかった

観測は**1日1回、朝9時**。データはそれ以外の時間には変わりません。
なのにこのアプリは、**画面を開くたびに**市のサイトへ取りに行っていました。

- 表示が遅い（毎回ネットワークの待ち時間が発生する）
- 市のサーバーに、意味のない負担をかける
- 取得が失敗しても、開いた人が「なんか出ないな」と思うだけで終わる

**データが更新される頻度と、取りに行く頻度が合っていない。** これが根っこでした。

### 作り替えたあとの形

```
GitHub Actions（毎朝1回）
  └ collect.py … 市のサイトから取得
       ├ snow_data_history.csv  全シーズンのデータ（これが「正」）
       ├ data/snow_data.json    最新シーズン（表示用）
       └ data/status.json       実行の記録
                  ↓ 自動でコミット
Streamlit版 … 保存されたCSVを読むだけ。取りに行かない
静的サイト（次回）… JSONを読んで描く
```

サーバーは借りません。費用もかかりません。
**GitHubのリポジトリが、そのままデータの置き場（データベース）になります。**

## ■ この日いちばん頭を使ったところ：「まだ無い」を失敗と呼ばない

作業したのは2026年9月。**オフシーズン**です。
市のサイトの最新は2026年3月で、次のシーズンのページが出るのは11月。

つまり9月〜10月は、**新しい数字が1つも出ない状態で、毎朝の自動実行を回す期間**になります。

ここで「データが取れなかった＝失敗」と作ってしまうと、どうなるか。
**6週間、毎朝失敗メールが届きます。** そして人は、毎日届く警告を必ず無視するようになります。

> これは、直そうとしている問題より悪い状態です。
> もともとの問題は「壊れても気づかない」こと。
> 毎朝オオカミ少年のメールを送る仕組みは、**気づける仕組みを自分の手で殺してしまいます。**

そこで、コードを書く前に「何を失敗と呼ぶか」を決めました。

| 状況 | 扱い |
|---|---|
| 一覧ページが取れない（通信エラー等） | **失敗**（市のURL変更かもしれない。人が見るべき） |
| 月別リンクが1件も見つからない | **失敗**（ページの作りが変わった） |
| ページはあるのに、表や日付の行が取れない | **失敗**（HTMLの変更。冬なら今すぐ知りたい） |
| 既存データと矛盾する（日数が大幅に減る等） | **失敗**（静かにデータが壊れるのを防ぐ） |
| **今シーズンのページがまだ無い** | **成功**（オフシーズンの正常な姿） |
| 今日の行がまだ「-」（欠測） | **成功**（更新前に取りに行っただけ） |
| 変化がなく、コミットするものが無い | **成功** |

### 「11月だからページがあるはず」と書いてはいけなかった

例年、新シーズンのページは11月に公開されます。
だから「11月になったのにページが無ければ失敗」としたくなります。私も最初はそう考えました。

ところが実際に市のサイトを調べてみると、
**17シーズンのうち、11月のページがあるのは12シーズンだけ**でした。

暖冬などで11月に雪が降らなければ、市は11月分を出さない年があるのです。

**もし暦の月で判定していたら、5シーズン分、1か月まるごと失敗メールが届いていました。**

判定の基準は「**新しいページが出たかどうか**」の一点だけにしました。
裏を返すと、シーズンの切り替わりは自動発見まかせになります。
11月のある朝、市がページを公開した瞬間に、仕組みが勝手に拾いはじめる――これが今回のねらいです。

## ■ 作ったもの：`collect.py`（696行）

（`_pick_data_table()` / `_to_float_or_none()` / `fetch_snow_data()`）を、

> **`--dry-run` は入門者にこそおすすめしたい仕組みです。**
> 「本番と同じ処理を走らせるけれど、何も壊さない」モードがあると、怖がらずに何度でも試せます。
> 今回も、確認作業のほとんどはこれで済みました。

**市のサーバーへの礼儀**として、毎朝の実行で取りに行くのは
一覧ページ1枚＋今シーズンの該当月1枚の**あわせて2回だけ**にしています。
全部の月を毎日取り直すようなことはしません。`--all` は最初の1回専用で、1.5秒の間隔を空けて回します。

## ■ 今回いちばんの山場：見えないマイナス

ここが、この日の作業で最も学びが多かったところです。**そして私が一度、間違えたところ**でもあります。

### ことの始まり

READMEの「今後の拡張案」に、第9回のあとで自分が書いた項目がありました。

> 積雪量がマイナスになった場合は None に変換せずそのまま表示し、潜在的なバグを検知できるようにする

現在のコードはこうなっています。

```python
match = re.search(r'\d+(?:\.\d+)?', x)   # 数字だけを取り出す
```

`\d` は「数字」だけを表します。マイナス記号は含まれません。
つまり `"-5"` を渡すと **`5.0` が返ります。符号が消えます。**

そしてこの結果、`main.py` にあった「負の値なら `None` にする」というガードは、
**一度も発火しない、動かないコード**になっていました。負の値がそこへ到達できないのですから当然です。

そこで私は、正規表現を符号ごと拾う形に直しました。

```python
match = re.search(r'-?\d+(?:\.\d+)?', x)  # 符号も拾う
```

### そして、いきなり2件釣れた

全期間を取り直すと、警告が出ました。

```
[WARNING] 積雪量が負値です: 2024年2月3日 新井消防署 raw='-18' -> -18.0
[WARNING] 積雪量が負値です: 2024年3月3日 新井消防署 raw='-10' -> -10.0
```

「拡張案に書いた仕掛けが、初回でいきなり2件釣った」――私はそう思いました。
前後の日は21cmと15cm。市の入力ミスだろう、と**結論を出してしまいました。**

### ところが、答えは第9回の記事に書いてあった

この作業ログを連載向けに整えるため、過去の記事を読み返しました。
すると**第9回**に、自分がClaude Codeへ渡した依頼が残っていました。

> HTMLに余分な文字列のマイナスが入っていて、降雪量、積雪量の数字の前または後ろに
> マイナス記号が付くことがある。数字のテキストだけを取得するように修正する。

そして、そこに貼られていたHTMLの実物。

```html
<td>30<span style="left: -5000px; width: 1px; height: 1px;
   overflow: hidden; position: absolute;">-</span></td>
```

**`left: -5000px`。画面の左5000ピクセル外に飛ばされた、見えない `-` です。**

問題の2024年2月3日のセルを直接見に行くと、こうなっていました。

```html
<td><span style="left: -5000px; ... position: absolute;">-</span>18</td>
```

見た目は「18」。でも素直に文字を取ると「-18」。

**市の入力ミスではありませんでした。私の変更が作り出した値でした。**
第9回で `\d+` にしたのは、まさにこの見えないマイナスを剥がすための、意図的な対処だったのです。

### 直し方：原因と対処の場所を分ける

正規表現をもとに戻せば、症状は消えます。でもそれでは「負の値を検知したい」という目的が果たせません。

そこで、**原因を潰す場所と、符号を読む場所を分けました。**

```python
def _cell_text(cell) -> str:
    """セルの文字列を取り出す。ただし画面に表示されない要素は先に捨てる。"""
    for el in cell.find_all(style=True):
        style = el["style"].replace(" ", "").lower()
        if "position:absolute" in style and ("left:-" in style or "top:-" in style):
            el.decompose()          # 画面外へ飛ばされた要素を丸ごと削除
    return cell.get_text(strip=True)
```

**見えない文字を先に剥がしてから、符号ごと数字を読む。**
こうすれば、隠しマイナスに引っかからず、しかも本物の負の値が来たときには気づけます。

結果、負値の警告は**0件**になりました。

### おまけ：もっと古い間違いも直った

取り直したデータの差分を見ると、**3行目**が直っていました。

```diff
- 2025,2,3,新井消防署,1035.0,35.0
+ 2025,2,3,新井消防署,10.0,35.0
```

セルの中身はこうでした。

```html
<td><span style="left: -5000px; ...">1035-</span>10</td>
```

隠れていたのは `1035-`、見えているのは `10`。同じセルで3つの実装を試すと、こうなります。

| 実装 | 読み取る値 |
|---|---|
| 第9回の `\d+` | **1035.0**（間違い） |
| 今回いったん入れた `-?\d+` | **1035.0**（間違い） |
| 今回の修正（隠し要素を剥がしてから） | **10.0**（正しい） |

つまりこの誤りは、**今回の変更とは関係なく、前からあったもの**でした。
「降雪1035cm」は、一晩で10メートル降った計算になります。グラフの縦軸は100cmまでなので、
**画面を見ても気づけなかったはずです。**

### 隠し文字の正体についての推測

3件ともパターンが同じでした。

| 日付 | 隠れている文字 | 見えている文字 |
|---|---|---|
| 2024-02-03 | `-` | `18` |
| 2024-03-03 | `-` | `10` |
| 2025-02-03 | `1035-` | `10` |

そう見ると、**隠れているのは「訂正される前の値」**のようです。
市の担当者が数字を直したとき、古い内容が消えずに画面外へ追いやられている――そう考えると辻褄が合います。
（あくまで推測です。断定はできません。）

**ページは、自分が訂正された記録を、見えない形で覚えている。** これは記事の山場になりそうです。

## ■ もうひとつの発見：存在しない「4月31日」

全期間の取得結果を点検していて、4月のデータが 90行（30日×3地点）のはずなのに、
**2015年4月と2025年4月だけ93行**になっていることに気づきました。

市のページを見に行くと、4月の表の最後に**空っぽの「31日」の行**がありました。テンプレートの消し忘れでしょう。

```
['31日', '', '', '', '', '', '']
['降雪量月計', '-', '2', '0']
```

値は全部空なので、そのままでも表示は壊れません。
ただ、存在しない日付がデータに混ざっているのは気持ちが悪いですし、
日付として扱う処理（グラフの横軸など）で事故のもとになります。

対処は2か所に入れました。

1. **取り込むとき**に、その月に実在しない日は捨てる（`calendar.monthrange()` で月の日数を調べる）
2. **CSVを読むとき**にも、同じ判定をして捨てる

なぜ2か所か。今回のデータ更新は **upsert**（同じ日のデータがあれば置き換える）方式なので、
**すでに入ってしまった行を消す経路がない**のです。
読み込み側にも判定を置くことで、次に走ったときに自然と消えます
（実際、次の実行で「実在しない日付の行を履歴から除きます: 6行」と出て消えました）。

> **自分で自分を直す仕組み**を1つ足しておくと、あとで手作業に呼び戻されずに済みます。

## ■ 追記ではなく upsert にした話

これまでは、取得したデータを履歴CSVに**追記**していました。
過去の月ならそれで問題ありません。でも**今月のデータは日々増えるし、訂正も入ります。**
追記のままだと、同じ日の行がどんどん増えていってしまいます。

そこで **「年・月・日・観測地点」の4つをキーにした upsert**（あれば置き換え、なければ追加）にしました。
何度実行しても、結果が同じになります。

これを **冪等（べきとう）** といいます。読み方が難しいのですが、
意味は「**何回やっても同じ結果になる**」だけです。

自動で毎日走る仕組みを作るとき、冪等かどうかは死活問題になります。
「途中で失敗したから、もう一度流す」が安全にできるかどうかが、ここで決まります。

早すぎると「取得は成功したけれど、今日の行はまだ空」という状態が毎朝続きます。
これは**記録の上では成功なのに中身が古い**という、いちばん気づきにくい壊れ方です。

まず10:30で始めて、10月のあいだ無人で動かしながら観察し、分かってから前倒しします。
そのために `status.json` に「取得できた最新の観測日」を記録するようにしました。
11月に入れば、毎朝それが当日になっているか前日のままかが、Gitの履歴から読めます。

（GitHub Actions の定時実行は、混雑で数分〜数十分遅れます。特に毎時0分が混むので `:30` にしてあります。）

## ■ 記事の構成案

材料が多いので、2本に分けるのがよさそうです。

### 第10回：なぜ、完成したアプリを作り替えるのか

- タイトル案：**「Streamlit Cloudでデータが保存されない／毎朝使う道具にするための作り替え」**
- この記事で分かること（案）
  - Streamlit Cloud では、CSVに書き込んでも再起動で消えてしまうこと
  - 「更新は1日1回なのに、見るたび取りに行く」構造がなぜ不利なのか
  - GitHub Actions ＋ リポジトリを、サーバーなしのデータ置き場として使う考え方
  - オフシーズンに「まだ無い」を失敗と呼ばないための、失敗の定義の決め方
- 学びポイント（案）
  - 保存するコードがあることと、データが残ることは別
  - 通知は、無視されはじめた時点で機能を失う
  - 「11月だから雪のページがあるはず」は人間の常識。データは5シーズンで裏切っていた

### 第11回：見えないマイナスに、自分で引っかかった話

- タイトル案：**「スクレイピングで数字がマイナスになる／画面外に隠されたHTMLの落とし穴」**
- この記事で分かること（案）
  - `left: -5000px` で画面外へ飛ばされた文字が、テキスト取得では拾われてしまうこと
  - 症状に合わせて正規表現をいじると、原因が別の場所に残り続けること
  - 原因を潰す場所と、値を解釈する場所を分ける考え方
  - 表示上のグラフでは気づけない誤り（降雪1035cm）の見つけ方
- 学びポイント（案）
  - 前回の自分の修正が、今回の自分を引っかけた。記録を読み返すと答えがあった
  - バグが2つ重なると、症状が見えなくなる
  - 異常値は潰さず、残して警告する。潰すと原因の切り分けができなくなる

### そのほか、使えそうな切り口

- **手で書いた台帳は必ず間違える**（誤ったラベルが自動生成で勝手に直った）
- **冪等であること**（追記から upsert へ。「もう一度流す」が怖くない状態を作る）
- **`--dry-run` のすすめ**（何も壊さずに本番と同じ処理を試せるモードを最初に作る）
- **存在しない4月31日**（テンプレートの消し忘れと、自分で自分を直す仕組み）
