## 1. 目的と背景

Streamlit版は、閲覧のたびに市サイトへスクレイピングしに行く作りになっている。
これを「GitHub Actions が毎朝1回取得してリポジトリにコミットし、表示側は保存されたデータを読むだけ」に変える。
その前半として、データ収集をStreamlit非依存のスクリプトへ切り出した。

### 変更の動機（3点）

1. **永続化の不全**：`save_history_data()` のローカルCSV書き込みは、Streamlit Cloud の一時ファイルシステムでは
   再起動のたびに消える。クラウド上で履歴蓄積が機能していなかった
2. **スリープ**：Community Cloud は低頻度アクセスでスリープし、復帰に数十秒かかる
3. **構造の不一致**：データは1日1回（9時観測）しか更新されないのに、閲覧のたびに取得していた

### 移行後の構成

```
GitHub Actions（毎朝1回・10:30 JST 予定）
  └ collect.py
       ├ snow_data_history.csv   全シーズン・唯一の正（upsert）
       ├ data/snow_data.json     最新データのあるシーズン・表示用
       └ data/status.json        実行記録
                  ↓ コミット
main.py（Streamlit）  … 履歴CSVを読むだけ（タスク5で改修）
静的サイト（次回）    … data/snow_data.json を読む
```

## 3. 設計判断

### 3-1. 失敗条件の定義

作業時点（2026年9月）はオフシーズンで、次シーズンのページは11月に出る。
「データが取れない＝失敗」とすると9〜10月のあいだ毎朝失敗通知が出るため、先に失敗の定義を確定させた。

| 状況 | 扱い | 実装箇所 |
|---|---|---|
| インデックスページが取得できない | 失敗（`exit 1`） | `run()` の `http_get` 例外 |
| 月別リンクが0件 | 失敗 | `discover_month_urls()` |
| 当シーズンのページはあるが、テーブルが無い／日付行が0件 | 失敗 | `parse_month_page()` |
| 既存の履歴と矛盾（月の日数が既存の8割未満） | 失敗 | `check_consistency()` |
| 当シーズンのページがまだ無い | **成功** | `run()` の `season_entries` 分岐 |
| 今日の行がまだ `-`（欠測） | 成功 | （そもそも判定しない） |
| 差分がなくコミットが出ない | 成功 | （ワークフロー側で処理） |

**暦の月を条件に使わない。** 判定基準は「新しいページが出たか」の一点のみ。
調査で11月ページが12シーズン分しかないと分かったため、暦で判定すると5シーズンで誤検知していた。

### 3-2. 年度（シーズン）の決め方

```python
def fiscal_year(year, month):
    return year if month >= 6 else year - 1   # 6月以降をその年度の始まりとする
```

依頼文の規則（11・12月→年度=西暦年−2018／1〜5月→年度=西暦年−2019）と等価。
6月を境にすることで、9月時点でも「当シーズン＝2026-27」と判定できる。

- 和暦変換：令和n年 = 2018 + n、平成n年 = 1988 + n
- 年度ラベル：`fy >= 2019` → 令和（2019は「令和元年度」）、`fy <= 2018` → 平成

### 3-3. 履歴CSVは追記から upsert へ

`(year, month, day, location)` をキーに置き換える。当月のデータは日々追加・訂正されるため、
追記だと同じ日の行が増え続ける。何度実行しても結果が同じになる（冪等）。

### 3-4. 取得回数

毎朝の実行は **インデックス1枚＋当シーズンの最新月ページ1枚の計2リクエスト**。
`--all` は初回バックフィル専用で、1.5秒間隔・識別用User-Agent付き。

## 5. 作業中に判明した問題と対処

### 5-1. 画面外に隠された文字を拾っていた（重大・自分で作り込んだ）

**経緯**

READMEの拡張案「積雪がマイナスになった場合は None に変換せずそのまま表示し、潜在的なバグを検知できるようにする」
に従い、`_to_float_or_none()` の正規表現を `\d+(?:\.\d+)?` → `-?\d+(?:\.\d+)?` に変更した。
`main.py:198-201` の負値ガードが発火しない死んだコードだったことも確認済みだった。

バックフィル後、負値の警告が2件出た。

```
[WARNING] 積雪量が負値です: 2024年2月3日 新井消防署 raw='-18' -> -18.0
[WARNING] 積雪量が負値です: 2024年3月3日 新井消防署 raw='-10' -> -10.0
```

前後の日が21cm・15cmだったことから**市の入力ミスと結論し、そのまま報告した（誤り）**。

**判明した原因**

連載記事（`note-letsmakeapp/02_arai-snow/09/index.md`）に、当時の依頼文とHTMLの実物が残っていた。
該当セルを再確認したところ、次の構造だった。

```html
<td><span style="left: -5000px; width: 1px; height: 1px;
   overflow: hidden; position: absolute;">-</span>18</td>
```

画面外（`left: -5000px`）に飛ばされた `-` が数字の前にある。表示は「18」。
第9回で `\d+` にしたのは、この隠し文字を剥がすための意図的な対処だった。
`-?\d+` への変更でそれを拾い、符号が反転していた。

**対処**

正規表現を戻すと「負値を検知したい」という目的が果たせないため、
**原因を除去する場所と、値を解釈する場所を分けた。**

```python
def _cell_text(cell) -> str:
    """セルの文字列を取り出す。ただし画面に表示されない要素は先に捨てる。"""
    for el in cell.find_all(style=True):
        style = el["style"].replace(" ", "").lower()
        if "position:absolute" in style and ("left:-" in style or "top:-" in style):
            el.decompose()
    return cell.get_text(strip=True)
```

`parse_month_page()` のセル取得を `c.get_text(strip=True)` から `_cell_text(c)` に差し替え。
`-?\d+` は維持。再バックフィルの結果、**負値の警告は0件**。

**副産物：旧実装にもあった誤りを検出**

差分に3行目があった。

```diff
- 2025,2,3,新井消防署,1035.0,35.0
+ 2025,2,3,新井消防署,10.0,35.0
```

該当セル：

```html
<td><span style="left: -5000px; ...">1035-</span>10</td>
```

同一セルでの各実装の挙動（素のテキストは `'1035-10'`）：

| 実装 | 結果 |
|---|---|
| 第9回の `\d+` | 1035.0（誤） |
| 今回の中間状態 `-?\d+` | 1035.0（誤） |
| 修正後（`_cell_text` 経由） | **10.0（正）** |

**この誤りは今回の変更とは無関係に前から存在していた。** グラフの縦軸上限は100cmのため、
1035という値は画面上では検出できない状態だった。

**隠し文字のパターン（3件）**

| 日付 | 隠れている文字 | 表示されている文字 |
|---|---|---|
| 2024-02-03 | `-` | `18` |
| 2024-03-03 | `-` | `10` |
| 2025-02-03 | `1035-` | `10` |

隠れている側が訂正前の値と見られるが、推測の域を出ない。

### 5-2. 実在しない「4月31日」の行

4月のデータが90行（30日×3地点）のはずが、2015年4月と2025年4月のみ93行だった。
市のページの4月の表に、空の「31日」行がある。

```
['31日', '', '', '', '', '', '']
['降雪量月計', '-', '2', '0']
```

対処は2か所。

1. `parse_month_page()`：`_is_real_date()`（`calendar.monthrange()` 利用）で取り込み時に除外
2. `load_history()`：CSV読み込み時にも同じ判定で除外

upsert は古い行を削除できないため、読み込み側にも置いて自己修復させた。
次の実行で「実在しない日付の行を履歴から除きます: 6行」が出て解消。

### 5-3. 地点名の異体字

2009年12月のページのみ「頚南消防署」。
行の出力は列位置で決まるため実害はないが、`_pick_data_table()` の「3地点名がそろうテーブル」判定が
外れて `tables[0]` にフォールバックしていた。`_normalize()` で `頚`→`頸` に寄せて判定するようにした。

### 5-4. pandas の FutureWarning

全欠測の月を `concat` する際に dtype 推定の警告が出た。
`parse_month_page()` の戻り値で `snowfall_cm` / `snowdepth_cm` を明示的に `float` へキャストして解消。

このログを元に記事を書くときの、材料になりそうな点だけ列挙する。

- **第9回で「完成」と締めている**ので、再開の理由から入る必要がある（読者は完結したと思っている）
- **保存するコードがあることと、データが残ることは別**（Streamlit Cloud の一時ファイルシステム）
- **オフシーズンに「まだ無い」を失敗と呼ばない**という設計判断。毎朝届く通知は無視されるようになる
- **暦で判定してはいけなかった**：11月のページは17シーズン中12シーズンにしか存在しない
- **見えないマイナス（5-1）**：前回自分が入れた修正に、今回の自分が引っかかった。
  原因は第9回の記事に書いてあった。症状に合わせて正規表現をいじると、原因が別の場所に残り続ける。
  「市の入力ミス」と誤った結論を出した経緯も含めて書ける
- **画面では気づけない誤り**：降雪1035cm はグラフの軸上限100cmのため見えなかった
- **手で書いた台帳は間違える**：誤ラベルが自動生成で解消した
- **冪等**（追記→upsert）と、**自己修復**（読み込み時にも不正行を除去）
- **`--dry-run` を最初に作る**価値
