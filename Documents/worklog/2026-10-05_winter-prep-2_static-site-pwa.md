## 2. 用語（初出のものだけ）

| 用語 | 意味 |
|---|---|
| **静的サイト** | サーバー側で処理をせず、置いてあるファイルをそのまま返すだけのサイト |
| **公開ルート** | 「このフォルダの中だけがURLで外から読める」という境界 |
| **CDN** | よく使う部品を誰でも借りられるように置いてある、世界中に配置された公共の倉庫 |
| **PWA** | Webサイトをスマホのアプリのように使えるようにする仕組み。ストアを通さない |
| **Service Worker** | ページとネットワークの間に立ち、通信を横取りできる常駐プログラム |
| **CDP** | Chrome DevTools Protocol。ブラウザを外から操作・計測するための窓口 |
| **gzip** | 配信時にファイルを圧縮する仕組み。テキストは1/3〜1/5になる |

## 3. ファイルごとの中身

### 3-1. `docs/index.html` — 画面すべて

**1ファイルで完結**させている。CSSもJavaScriptもインライン。
理由は、ファイルを分けるとその数だけ通信が増え、起動が遅くなるため。15KBなら分ける利点がない。

構成は3段。

```
header   ❄ 妙高の雪
         2026年3月23日 の観測          ← 観測日をいちばん大きく
         （オフシーズンのみ）注記

cards    新井消防署            —  記録なし
         頸南消防署          5 cm  前日比 -9  降雪 —
         妙高市役所 妙高支所   —  記録なし

chart    シーズンの推移   2025年11月1日 〜 2026年3月23日
         [新井][頸南][妙高支所]        ← 地点切り替え
         降雪=棒（青）／積雪=線（オレンジ）

footer   最終更新 2026-10-05 19:14     ← 古い数値を見分ける最後の砦
         観測時刻 9時／…
         「—」は市の記録に値がない日です（ゼロではありません）
```

#### 観測日を最上段に置いた理由

欠測があるため、**「今朝の数字」が今日のものとは限らない**。
いまのデータなら最新は2026年3月23日で、今日（10月5日）ではない。
ここを見落とすと、半年前の数値を今朝の数値として読んでしまう。

#### 主な処理

| 関数 | 役割 |
|---|---|
| `fmtDate()` | `2026-03-23` → `2026年3月23日` |
| `fmtDiff()` | `15` → `+15`（オレンジ）／`0` → `±0`（灰）／`-9` → `-9`（水色） |
| `fmtUpdated()` | `2026-10-05T19:14:51+09:00` → `2026-10-05 19:14` |
| `renderCards()` | 3地点のカードを描く |
| `renderChart()` | タブを作り、既定の地点でグラフを描く |
| `whenChartReady()` | Chart.js が使えるようになるまでグラフだけ待たせる |

#### 地点の並びは固定

`locations` の順のまま。値のある地点を上に寄せる案もあったが、
**毎朝見る道具は位置が動かないほうが目的の地点を早く見つけられる**と判断した。
値が無いカードは背景を暗くして沈めている。

#### グラフの既定の地点は「最新日に値がある地点」

固定にすると、いまのように新井が欠測の時期に**空のグラフが最初に出る**。
最新日に値がある地点を先頭から探して選ぶ。いまなら頸南消防署。

### 3-2. `docs/manifest.json` — アプリ名・アイコン・全画面の指定

PWAの3点のうちの1枚目。**ブラウザに「これはアプリとして扱ってよい」と伝える名刺**。

```json
{
  "name": "妙高の雪",
  "start_url": "./",
  "scope": "./",
  "display": "standalone",
  "theme_color": "#0d1b2a",
  "background_color": "#0d1b2a",
  "icons": [ { "src": "icons/icon-192.png", "sizes": "192x192", "purpose": "any maskable" }, … ]
}
```

- `display: standalone` … **アドレスバーが消えて全画面になる**。これが「アプリらしさ」の正体
- `start_url` / `scope` を **`"./"`（相対）** にしている。詳細は「5-1」
- `purpose: "any maskable"` … Androidが端末ごとの形（丸・角丸など）に切り抜いても欠けないという宣言。
  そのためアイコンの絵柄は中央60%に収めてある

### 3-3. `docs/service-worker.js` — 通信を横取りして保存分を返す番人

PWAの3点のうちの2枚目。**ここが今回いちばん設計を考えた場所。**

#### キャッシュ戦略を2つに分けた

**「速さ」と「新しさ」は競合する。**だからファイルの種類ごとに決めるしかない。

| 対象 | 戦略 | 理由 |
|---|---|---|
| シェル（HTML・Chart.js・アイコン・manifest） | **キャッシュ優先** | 毎朝同じものを読むだけ。ネットワークを待たずに即出す |
| `data/snow_data.json` | **ネットワーク優先、ただし1.5秒で打ち切り** | 数字は新しいほうがよい。でも待ちすぎてはいけない |

#### 待ち時間の上限（1.5秒）を設けた経緯

最初は「ネットワーク優先、**失敗したら**キャッシュ」だった。機内モードのテストは通る。

しかし**機内モードはやさしい条件**だと気づいた。通信が即座に失敗するので、すぐ諦めてキャッシュを返せる。

**本当に困るのは「電波が弱いが繋がっている」状態。**通信はすぐには失敗せず、何十秒も待たされる。
雪の朝の山あいは、まさにこれが起きる場所。**完了条件の「3秒」を、いちばん大事な場面で破る。**

```js
const DATA_TIMEOUT_MS = 1500;

function dataResponse(network) {
  return caches.match("./" + DATA_PATH).then((cached) => {
    if (!cached) return network;            // 保存分が無ければ待つしかない
    return new Promise((resolve) => {
      const finish = (res) => { … };
      timer = setTimeout(() => finish(cached), DATA_TIMEOUT_MS);  // 時間切れ→保存分
      network.then((res) => finish(res && res.ok ? res : cached))
             .catch(() => finish(cached));
    });
  });
}
```

時間切れで保存分を返したあとも、**通信は裏で走り続けてキャッシュだけ更新する**（次に開いたときに効く）。
そのために `event.waitUntil(network)` で Service Worker を生かしておく。
なお `waitUntil` は fetch ハンドラの中で**同期的に**呼ぶ必要がある（後から呼ぶとエラーになる）。

#### install時にデータもキャッシュする

最初の実装では `install` でシェルだけ保存していた。検証したらデータのキャッシュが**できていなかった**。

理由：**初回アクセスでは、ページがデータを取りに行く時点でまだ Service Worker が通信を見張っていない。**
install は済んでいても、そのページの通信はもう始まってしまっている。

これが無いと「**一度も開き直さずに圏外になった**」場合に何も出せない。
`install` で `cache.add("./data/snow_data.json")` を追加して解決した。

#### バージョン

```js
const VERSION = "v2";
const SHELL_CACHE = `miyoko-snow-shell-${VERSION}`;
```

配信物を更新したらここを上げる。`activate` で、名前が一致しない古いキャッシュを消す。
これをしないと、**古いファイルがいつまでも返り続ける**ことになる。

`skipWaiting()` と `clients.claim()` も入れている。新しい版をすぐ使うため。
毎朝1回しか開かない道具なので、**古い版に張り付いたまま気づかない状態のほうが困る**という判断。

### 3-4. アイコン3枚と `tools/make_icons.py`

PWAの3点のうちの3枚目。

| ファイル | 用途 |

| `icon-512.png` | 起動時のスプラッシュ画面など |

1. ホーム画面ではアイコンの下にアプリ名が出る。絵に地名を重ねる必要がない
2. 文字を入れるとフォント（Hiragino）に依存し、**他の環境で再生成できなくなる**

なめらかに見せるため4倍の大きさで描いてから縮小している（スーパーサンプリング）。

## 4. つまずきと解決（時系列）

**この節がいちばん振り返る価値がある。**手順どおり進んだ部分より、ここで時間を使った。

### 4-1. 「ブラウザが無い」と誤報した（私のミス）

環境調査で、zshのグロブ（`*` を使ったパス指定）がマッチせずエラーになり、
**検出用のループ全体が実行されないまま**「ブラウザが無い」と報告した。

実際には `/Applications/Google Chrome.app` があった。
後で `ls /Applications` を素直に実行して気づいた。

> **教訓**：「無い」と判定するコマンドは、**成功時の出力も確認する**こと。
> 何も出ないのは「無い」なのか「動いていない」なのか区別がつかない。

### 4-2. 「横スクロールが起きている」と誤報した

Chromeをヘッドレス（画面を出さずに動かすこと）で `--window-size=375,812` を指定して
スクリーンショットを撮ったところ、右端が切れていた。横スクロールだと判断した。

**これも誤り。**実際にページ内で測ると viewport は **485px** だった。
macOSのウィンドウ最小幅に阻まれて `--window-size` が効かず、**485pxで描画した画像を375pxに切り取っていた**だけ。

| 試した方法 | 結果 |
|---|---|
| `--headless=new --window-size=375,812` | viewport 485px |
| `--headless=old` | viewport 485px |
| `--force-device-scale-factor=1` を追加 | viewport 485px |
| **CDPで `Emulation.setDeviceMetricsOverride`** | **viewport 375px** |

CDP（Chrome DevTools Protocol）で端末エミュレーションを直接指定して解決。
実測は **document幅375px・はみ出し要素0件**で、横スクロールは最初から起きていなかった。

> **教訓**：**計測の道具が正しく効いているかを、まず確かめる。**
> 「375pxを指定した」と「375pxで描画された」は別。

### 4-3. 低速回線で数値が出るまで1746msかかっていた

回線を絞って（遅延150ms / 1.6Mbps）測ると、内訳はこうだった。

```
chart.umd.min.js  1184ms   ← これを待っている
snow_data.json     316ms
数値が出るまで     1746ms
```

Chart.js を `<script src="…">` で普通に読み込むと、**その取得が終わるまで下の処理が始まらない。**
しかし**数値の表示にグラフ部品は要らない。**

`defer` を付けて切り離し、グラフだけ Chart.js が使えるようになってから描くようにした。

| | 改善前 | 改善後 |
|---|---|---|
| 初回（低速回線） | 1746ms | **556ms** |
| 2回目（SWキャッシュ） | — | **25ms** |

副産物として、**Chart.js の読み込みに失敗しても数値だけは出る**という頑丈さも手に入った。

### 4-4. 計測プローブが数値を取りこぼした

4-3の改善後、「数値が出るまで」が `None` になった。
プローブ（計測用の小さな監視コード）を `DOMContentLoaded` のタイミングで仕掛けていたが、
**改善によって数値がそれより前に出るようになった**ため、監視開始に間に合わなかった。

ページ読み込みの最初から10ms間隔で監視する方式に変えて解決。

> **教訓**：**速くすると、計測のほうが追いつかなくなることがある。**

### 4-5. オフライン検証が「見かけ上」成功していた（2回）

Service Worker のオフライン動作を検証したら成功した。しかし**キャッシュの中身を見ると `data` が無かった**。

データを返していたのは**ブラウザのHTTPキャッシュ**（Service Workerとは別の、ブラウザが元々持っている仕組み）だった。
つまり**Service Workerが働かなくても表示できていた**だけで、検証になっていなかった。

対策を2つ入れた。

1. `install` でデータもキャッシュする（3-3参照）
2. **検証の前に `Network.clearBrowserCache` でHTTPキャッシュを消す**

消したうえで再検証して、はじめて「Service Workerが返している」と言える状態になった。

> **教訓**：**成功したテストこそ、「なぜ成功したか」を確かめる。**
> 冬支度①でも同じ型の失敗（通るけれど何も見ていないテスト）をしている。

### 4-6. ネットワーク絞りが Service Worker に効かなかった

「電波が弱いが繋がっている」状態を作るため、CDPで遅延10秒を設定して測ったら、
**22msで数値が出た**。速すぎる。

原因：**CDPのネットワーク絞りはページに対する設定で、Service Worker の通信には適用されない**
（Service Worker は別のプロセス扱い）。つまり遅い回線を通っていなかった。

解決：**Service Worker のソースをページの中に読み込み、`caches` と `fetch` を差し替えて
`dataResponse()` を直接呼ぶ**方式に変えた。

```
保存分あり・通信が返らない   1503ms  → 保存分を返した（上限どおり）
保存分あり・通信が速い          0ms  → 通信を返した
保存分あり・通信が失敗          0ms  → 保存分を返した
保存分なし・通信が速い          0ms  → 通信を返した
```

### 4-7. ブランチを消したら Pages の設定ごと消えた

実機確認のため、**マージ前にブランチから Pages を公開**した（本番と同じHTTPS条件で試せる）。
マージ後にブランチを削除したところ、**Pages の設定そのものが消えて公開が404になった。**

`main` / `/docs` で再設定して復旧。URLは変わらなかった。

> **教訓**：Pages の公開元にしているブランチを消すときは、**先に公開元を切り替える。**

## 5. 設計上の判断

### 5-1. パスはすべて相対で書く

**今回いちばん効いた判断。**

公開URLは `https://kehorikawa.github.io/arai_snow_st/` で、**サイトのルートではなくサブフォルダ**。
`/manifest.json` のようにルートから書くと `https://kehorikawa.github.io/manifest.json` を見に行き、**すべて404**になる。

| 場所 | 書き方 |
|---|---|
| `<link rel="manifest" href="manifest.json">` | 相対 |
| `navigator.serviceWorker.register("service-worker.js")` | 相対 |
| manifest の `start_url` / `scope` | `"./"` |
| Service Worker のキャッシュ対象 | `"./"`, `"./index.html"`, … |

Service Worker の中の相対パスは、**SW自身の場所**を基準に解決される。
`service-worker.js` が `/arai_snow_st/` にあるので、`"./index.html"` は `/arai_snow_st/index.html` になる。

本番で検証したところ **scope が `https://kehorikawa.github.io/arai_snow_st/` に正しく収まり**、
manifest もエラー0件だった。

### 5-2. 欠測は「—」＋「記録なし」。`0cm` とは書かない

市は**ゼロのとき `0` と明記している**（降雪678行・積雪298行）。同じ列に `0` と `-` が併存するので、
**`-` はゼロの意味では使われていない。**

2024年2月の新井消防署が分かりやすい。**2日は `0`、3日は `-`。**

ラベルは「観測なし」ではなく**「記録なし」**にした。
言えるのは「市の記録に値が無い」ことだけで、観測行為そのものの有無は分からないため。

#### 直近の値を繰り越す案を採らなかった理由

値が無い地点について、`series` から直近の値を探して出す案（依頼者は当初こちら寄りだった）。
履歴で調べたところ、値が無いときの「直近の値までの日数」はこうだった。

| 地点 | 中央値 | 平均 | 30日超 |
|---|---|---|---|
| 新井消防署 | 7日 | **39日** | 75件 |
| 妙高市役所 妙高支所 | 5日 | 17日 | 18件 |
| 頸南消防署 | 1日 | 1日 | 0件 |

真冬に限っても新井は中央値3日前。**3秒で読む画面に3日前の数値を出すのは、
いちばん避けたかった誤解（古い数字を今朝の数字と読む）を招く。**

さらに、11月・4月の新井の「-」は**低標高で雪が無い**ことを意味している可能性が高い。
古い値を繰り越すと、**雪が無いのに雪があると表示する**ことになる。

#### 「画面が寂しい」問題は真冬にはほぼ起きない

3地点がそろわない日の割合は、11月92.9%・4月88.3%に対し、**真冬（12〜2月）は14.5%**。
そして**頸南消防署は全期間で欠測1件のみ**なので、どの日も最低1地点は数字が出る。

### 5-3. 縦スクロールは許容する

要求は「**横**スクロールが起きない」と「**①数値ファースト**がスクロールせずに読めること」の2つ。
②グラフを見るために縦に動くのは構成上の前提。

実測で**カード下端386px**（オフシーズン）／**320px**（冬・注記が消えるため）。
いちばん画面の短い iPhone SE（667px）でも余裕がある。

## 10. 記事にする際の要点

### 題材1：CDNから借りるか、自分で持つか

**CDNとは**、よく使う部品（グラフを描くライブラリなど）を誰でも借りられるように、
世界中に置いてある公共の倉庫のこと。URLを書くだけで使える。

**借りる書き方**

```html
<script src="https://cdn.jsdelivr.net/npm/chart.js@4.4.7/dist/chart.umd.min.js"></script>
```

**自分で持つ書き方**（今回はこちら）

```html
<script src="vendor/chart.umd.min.js" defer></script>
```

**自分で持つほうを選んだ理由**

1. **オフラインで開ける。**外部の倉庫は、圏外では当然読めない。
   Service Workerで外部CDNをキャッシュすることもできるが、自分で持つほうが単純
2. **速い。**別のドメインに繋ぎに行くと、名前解決と接続で1往復増える
3. **将来壊れない。**CDNのURLが変わったり、サービスが終わったりしても影響を受けない
4. **70KBは軽い。**gzip後69.9KB（生205.9KB）。持つコストが小さい

**引き換えに失うもの**：ライブラリの更新を自分でやることになる。
ただし**今回はそれが利点でもある**。毎朝自動で動く道具なので、
**知らないうちに外部の部品が変わって壊れる**ほうが怖い。更新は自分のタイミングで行いたい。

**Plotly.js（約1MB）とChart.js（gzip後69.9KB）**

Streamlit版と見た目を揃えるなら Plotly.js（同じライブラリのJS版）という手もあった。
だが約1MBは「3秒で開く」という目標に反する。**見た目の統一より起動速度を採った。**

**実測した重み**：低速回線での初回、Chart.js の取得に **1184ms**。
これが「数値はグラフ部品を待つ必要がない」（＝`defer`）という判断につながった。

### 題材2：PWAとは結局ファイル3枚

**PWAとは**、Webサイトをスマホのアプリのように使えるようにする仕組み。ストアを通さない。

**実体は3枚。既存のページを作り直すのではなく、数枚足すだけ。**

| ファイル | 役割（1行） |
|---|---|
| `manifest.json` | アプリ名とアイコンと全画面表示の指定 |
| `service-worker.js` | 通信を横取りして保存分を返す番人 |
| アイコン画像 | ホーム画面の絵 |

既存の `index.html` に足したのは、`<link rel="manifest">`、`<link rel="apple-touch-icon">`、
Service Workerを登録する5行だけ。**画面のコードは1行も書き換えていない。**

**キャッシュ戦略を2つに分けた理由**

「速さ」と「新しさ」は競合する。全部キャッシュ優先にすれば速いが数字が古くなる。
全部ネットワーク優先にすれば新しいが遅い。**ファイルごとに決めるしかない。**

- シェル（HTML・Chart.js・アイコン）＝**キャッシュ優先**。毎朝同じものなので、起動を速くする
- `snow_data.json`＝**ネットワーク優先**。数字は新しいほうがよい

**さらに、ネットワーク優先には上限が要る**という話が、今回いちばんの学びだった。
機内モードのテストは通るのに、「弱いが繋がっている」状態では何十秒も待たされる。
1.5秒で打ち切って保存分を出すようにした。**「圏外」より「電波が弱い」ほうが難しい。**

**実機で詰まった点**（Android版）

- Chromeが「**インストール**」と「**ショートカットを作成**」の2択を出す。
  **インストールを選ぶ**と全画面のアプリになり、ショートカットだとブラウザのタブが開くだけ
- 「インストール」が選択肢に出ること自体が、
  **manifest・Service Worker・アイコンが揃っているとブラウザが判断した証拠**
- **Service Workerを更新したら、アプリを2回起動する必要がある**（1回目で入れ替わり、2回目から有効）

**iOSについては実機未確認。**`apple-touch-icon` を指定しないとホーム画面にアイコンが出ない、
という対策は入れてあるが、確認できていない。iPhoneを持つ方に見てもらう必要がある。

### 題材3：なぜ `docs/` なのか（公開ディレクトリの名前は自分で決められない）

**静的サイトの「公開ルート」とは**、「このフォルダの中だけがURLで外から読める」という境界のこと。

**GitHub Pages の「ブランチから公開」には、`/（ルート）` と `/docs` の2択しかない。**
だから `docs/` は**ドキュメント置き場ではなく「公開される側」**を意味している。
**この名前は自分で選んだのではなく、GitHubが決めている。**

**依頼者が戸惑った理由**

このリポジトリには既に `Documents/`（要件メモ・作業ログ）と `plans/`（移行計画）がある。
そこに `docs/` が増えると、**ドキュメント置き場が3つあるように見える。**

```
arai_snow_st/
├── Documents/   ← 文書（作業ログ・メモ）
├── plans/       ← 文書（計画）
└── docs/        ← 文書ではない。公開されるサイト本体
```

**用語の意味が「文書」から「公開物」に反転している。**
英語の docs は documents の略なのに、ここでは document の置き場ではない。

**任意の名前（`public/` など）にする道もある**

Pages の公開方法を「ブランチから」ではなく「GitHub Actions から」に切り替えると、
どのフォルダを公開するかをワークフローの中で指定できる。名前は自由になる。

**それを選ばなかった理由**

1. **ワークフローが1本増える。**いまは毎朝のデータ収集の1本だけで済んでいる
2. **11月の降雪に間に合わせるのが最優先。**仕組みを増やすほど確認する箇所が増える
3. **後から変えても公開URLは変わらない。**つまり**可逆**。急いで決める必要がない

**`snow_data.json` を `docs/data/` に移した話は、同じことの裏表**

公開されるのは `docs/` の中だけなので、**外から読ませたいデータはその中に置くしかない。**
`docs/index.html` から `../data/snow_data.json` を読もうとすると404になる。

```python
# collect.py
DOCS_DATA_DIR = BASE_DIR / "docs" / "data"
SNOW_JSON = DOCS_DATA_DIR / "snow_data.json"
```

**データの置き場所が、URLの都合で決まる。**
これが Streamlit（Pythonが手元のファイルを自由に読む）との一番の違い。

Streamlit版では `snow_data_history.csv` がリポジトリのどこにあっても読めた。
静的サイトでは「**ブラウザから見えるURLに存在するか**」がすべて。
`data/status.json` を `data/` に残したのも同じ理由で、**サイトから読まないものは公開しなくてよい。**

### その他、使えそうな切り口

- **計測の道具が効いているかを先に確かめる**（`--window-size` が効かず485pxで描画されていた）
- **成功したテストこそ「なぜ成功したか」を確かめる**（HTTPキャッシュのせいで、
  Service Workerが働かなくてもオフライン表示できていた）
- **速くすると計測が追いつかなくなる**（プローブが数値の表示を取りこぼした）
- **機内モードはやさしい条件**。本当に困るのは「弱いが繋がっている」
- **マージ前にブランチからPagesを公開して実機確認する**という手（ただしブランチを消すと設定ごと消える）
- **欠測とゼロを区別する**。市は `0` と `-` を書き分けていた
