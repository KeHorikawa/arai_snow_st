## 1. いまの構成（2026-09-26 時点）

### 使っているGitHubの機能は2つ、役割が違う

混同しやすいので最初に分けておく。

| 機能 | 役割 | 状態 |
|---|---|---|
| **GitHub Actions** | 毎朝データを取ってきてコミットする（**データの供給**） | ✅ 稼働中 |
| **GitHub Pages** | 静的サイトを配信する（**表示の場所**） | ⬜ 冬支度②で着手 |

**今回作った GitHub Actions は、静的サイトのためのものではない。**
いま現在は Streamlit版のために働いている。Streamlit版はこれまで自分で市サイトへ取りに行っていたが、
それをやめて Actions が用意したファイルを読む側に回った。

### 全体図

```
                GitHub Actions（毎朝 10:30 JST）
                        │ collect.py
                        ▼
        ┌───────────────┴───────────────┐
        ▼                               ▼
snow_data_history.csv            data/snow_data.json
（全18シーズン・8,796行）          （最新シーズンのみ・15KB）
        │                               │
        ▼                               ▼
   Streamlit版                   静的サイト（冬支度②）
   ローカル / Streamlit Cloud     GitHub Pages
        ✅ 稼働中                      ⬜ 未着手
```

サーバーなし・費用ゼロ・コールドスタートなし。**リポジトリがそのままデータの置き場になっている。**

### 2つの表示側は、読むファイルが違う

| 表示側 | 読むファイル | 用途 |
|---|---|---|
| Streamlit版 | `snow_data_history.csv`（全18シーズン） | じっくり見る道具。年月を選んで過去を見る |
| 静的サイト（次回） | `data/snow_data.json`（最新シーズンのみ） | 毎朝3秒の道具 |

JSONには当シーズン分しか入っていないため、**Streamlit版の「18シーズンから選ぶ」機能は賄えない**。
だからタスク5では、あえてJSONではなくCSVを読ませている。

### 当面の方針

計画（`plans/`）の共通ルールに、こうある。

> **Streamlit版は移行完了まで止めない**。新版が完了条件を満たしてから旧版をアーカイブする。

つまり当面は両方が並走する。静的サイトが「ホーム画面から3秒で今朝の雪が見える」を満たした時点で、
Streamlit版をどうするか判断する。**両方を恒久的に維持すると決まっているわけではない。**

## 2. 毎日コミットが積み上がる運用について

### これは「Git scraping」という定着した手法

2020年ごろに Simon Willison が名付けて広まった、「**リポジトリをデータベースとして使う**」やり方。
小規模なデータ収集では定番の部類に入る。

採る理由：

- サーバーを借りずに済む（費用ゼロ）
- 履歴が勝手に残る。**いつ値が変わったかがdiffで分かる**
- バックアップと世代管理をGitがやってくれる

ただし、**大きな業務リポジトリでアプリのコードとデータを同居させるのは一般的ではない。**
今回のような小さな個人開発だから成り立つ形である、という区別はしておく。

### 欠点：履歴が埋まる

冬になれば1日1件、**年365件**のコミットが積み上がる。コードの作業履歴が埋もれる。
これはこの手法の既知のトレードオフ。

対策として、**コミットメッセージを `data: update snow data (日付)` という機械的な形にしてある。**

### 見分け方

手元：

```bash
git log --author="Keiichi"                      # 自分のコミットだけ
git log --author="github-actions"               # botのコミットだけ
git log --invert-grep --grep="^data: update"    # データ更新を除外
git log -- main.py collect.py                   # コードを触ったコミットだけ
```

GitHubの画面：URLに `?author=` を付ける。

```
https://github.com/KeHorikawa/arai_snow_st/commits/main?author=KeHorikawa
```

コミット一覧にも作者の絞り込みがある。botのコミットにはロボットのアイコンが付くので、目でも区別できる。

### それでも気になる場合の選択肢

| 方法 | 効果 | 代償 |
|---|---|---|
| **A. いまのまま** | 追加作業なし | 履歴は混ざる。フィルタで対応 |
| B. データ専用ブランチに分ける | mainの履歴が静かになる | Streamlit Cloud も静的サイトも参照先の調整が必要。**冬支度②の設計に影響する** |
| C. データ専用リポジトリに分ける | 完全分離 | リポジトリを2つ行き来する。個人開発には重い |
| D. 定期的に履歴をまとめる | 履歴が縮む | 履歴の書き換えは事故のもと。**非推奨** |

**2026-09-26 時点の判断：A のまま。** 理由は2つ。

1. 毎日のコミットには目的がある。10月の無人稼働の成功率を見る「成績表」であり、60日ルールの保険でもある
2. B は冬支度②と衝突する。静的サイトは Pages が配信するブランチからJSONを読むため、
   **データの置き場所を先に決めると次回の設計の選択肢が狭まる**

分けるとしても、**冬支度②で配信のかたちが決まってから**のほうが安全。

### 補足

- **リポジトリは太らない**：オフシーズンで1日3〜4行、冬でも20〜40行程度。年間で数MB増える程度
- **無限ループにはならない**：`GITHUB_TOKEN` によるpushはワークフローを起動しない仕様
- **節目にはタグ**：`git tag -a winter-prep-1 -m "..."` で区切りを残すと、データコミットの中でも位置が分かる

## 3. 将来：スマホで過去検索まで行う場合の技術的制約

「簡易はスマホ、詳細はPCのStreamlit」という現在の切り分けを、
将来スマホ側へ寄せる（＝Streamlit版の機能を静的サイトへ移す）場合に何が問題になるか。

### 結論：技術的に「できない」ことはない

判断が要るのは**画面設計**と、**どこまで作り込むか**だけ。

### データ量は制約にならない（実測）

| 配信のしかた | サイズ | gzip後 |
|---|---|---|
| 履歴CSVをそのまま | 313KB | **38KB** |
| 全期間を1つのJSONに | 999KB | **42KB** |
| シーズン別に17分割 | 各58KB | 各7KB程度 |

**17シーズン8,796行が、圧縮して38KB。** 写真1枚より軽い。
GitHub Pages は自動でgzip配信するので、**分割もせず一度に全部読んでよい。**
「過去検索はデータが重いから無理」という心配は、このアプリでは起きない。

### 実際に効いてくる制約は4つ

#### ① 処理を書く場所が変わる（Python → JS、または事前計算）

閲覧時にできるのはブラウザのJavaScriptでできることだけ。pandas は使えない。

いまの機能（年月と地点で絞ってグラフを描く）は、JSの `filter` で数行。移植の難所にはならない。

ただし将来、平均・最大・偏差などの集計を入れるなら選択肢は2つ。

- **`collect.py` が毎朝計算してJSONに入れておく**（推奨。Pythonのまま書ける）
- ブラウザ側でJSで計算する

**「Pythonでやる処理を、閲覧時から収集時へ前倒しする」**という発想の切り替えが要る。これが一番大きな違い。

#### ② Streamlitがタダでくれていたものを、自分で作る

これが**本当のコスト**。技術的な壁ではなく手間の話。

| Streamlit | 静的サイトでは |
|---|---|
| `st.selectbox` | `<select>` ＋ イベント処理を自分で書く |
| サイドバーのレイアウト | CSSで自分で組む |
| ウィジェット変更で自動再実行 | 再描画を自分で呼ぶ |
| `session_state` | URLのクエリパラメータなど |

ただし `session_state` については、**URLに持たせるほうがスマホでは優れている。**
「2026年2月の新井消防署」の状態がそのままリンクになるので、**知人に送れる。** Streamlitでは難しい。

#### ③ 画面は「移植」ではなく「作り直し」になる

**ここが唯一、判断が必要な制約。**

いまのStreamlit版は「年・月・地点の組を3つ選んで、縦にグラフを3つ並べる」形。
これを375pxの画面にそのまま持ってくると、かなり窮屈になる。

技術的に不可能なのではなく、**スマホでは違う見せ方が要る**ということ。たとえば、

- 3件同時ではなく1件ずつ＋スワイプで切り替え
- 年月の選択を、プルダウン3段ではなく別の選び方に
- グラフの凡例や軸ラベルを間引く

**「PC版の機能をスマホへ移す」のではなく、「同じデータで、スマホ用の道具を作る」**と考えたほうがうまくいく。

#### ④ GitHub Pages は公開のみ

無料枠では非公開サイトにできない。今回は市の公開データなので問題にならないが、性質として知っておく。

Pages の制限（リポジトリ1GB・転送100GB/月・ビルド10回/時）は、このアプリの規模では届かない。

### グラフ描画ライブラリのトレードオフ

| | サイズの目安 | 見た目 |
|---|---|---|
| **Plotly.js** | 約1MB | **いまのStreamlit版とほぼ同じ**（同じライブラリのJS版） |
| **Chart.js** | 約70KB | 自分で寄せる必要あり |

「ホーム画面から3秒」を目標にするなら **Chart.js が有利**。計画でもChart.jsを選んでいる。
ただし「見た目を揃えたい」が優先なら Plotly.js という手もある。

### Streamlit版を残すかどうか

技術的には静的サイトが全機能を吸収できるので、計画どおり「旧版をアーカイブ」も選択肢に入る。

ただし**残す理由もある**。

- **Pythonで手早く試せる場所**として価値がある。新しい分析（前年比較、統計）をまずStreamlitで試し、
  良ければ静的サイトへ、という使い分けができる
- 静的サイト側の実装を、その分だけ軽く保てる

「スマホ＝日常の道具、PC＝実験と深掘り」という切り分けを、
**機能の制約からではなく、役割の違いとして残す**選択もありうる。

### まとめ

| 論点 | 制約か |
|---|---|
| データ量・通信 | ❌ 問題にならない（38KB） |
| 機能の再現可能性 | ❌ すべて実現できる |
| 画面設計 | ⚠️ 作り直しになる。移植ではない |
| 実装の手間・JS学習 | ⚠️ ここが実質的なコスト |
| 非公開にしたい | ⚠️ GitHub Pages無料枠では不可 |

### 関連する保留事項

- **「🔄 データを再読み込み」ボタン**：スクレイピングを外したことで役割が変わった
  （いまは「保存ファイルを読み直す」）。将来、静的サイトへ移行する段階で自然に外せる。急ぐ必要はない

## 4. 冬支度①で判断した箇所と、その根拠（要約）

詳細は worklog にあるが、通して見たいときのために一覧にしておく。

| 判断 | 決め手 |
|---|---|
| 隠し文字を剥がしてから読む | 症状を消すのと原因を取り除くのは別。正規表現を戻すだけでは本物の負値も見逃す |
| 失敗条件を「日数が既存の8割未満」 | 誤検知が一番高くつく。冬の朝に誤報が来ると通知を無視する癖がつく |
| `--all` を2009年まで（97ページ） | 17シーズンすべて同じ構造だと実測できた。取得は一度きりで済む |
| 再読み込みボタンを残した | 連載第9回で意図して追加されたもの。消さずに役割を移した |
| 実行時刻を10:30 JST | 遅れは可逆だが、早すぎると「緑なのに中身が古い」という気づきにくい壊れ方になる |
| JSONに昨シーズンを入れる | 空だと10月に静的サイトを実データで試せない |
| 失敗を記録してから落とす | 即失敗させると `status.json` がコミットされず、原因が履歴に残らない |

**通底している考え方**：①②⑤⑦はいずれも「**壊れたときにどうなるか**」から逆算している。

「冬のあいだ、手を触れずに毎朝動く道具」という目的からすると、
**成功時の振る舞いより、失敗時の振る舞いのほうが重要**だった。
